# garmin-running-analysis

A personal running analysis tool for one Garmin account. It pulls the full activity history (per-second FIT data, daily summaries, and a few Garmin metrics) into a local archive, then computes its own transparent, tunable metrics instead of relying on Garmin's black-box numbers:

- **Aerobic fitness trend**: grade-adjusted pace at a fixed reference heart rate, fitted on steady-state seconds of each run, shown as weekly medians with a 4-week rolling median.
- **Training load**: Banister TRIMP per activity, CTL/ATL/TSB trends, and a load-spike warning.
- **Weekly volume**: running distance per week (walking seconds left out), with running pace.
- **Long runs**: efficiency factor and aerobic decoupling for runs of an hour or more.
- **Race prediction**: VDOT from recent all-out races, with Riegel and Garmin's Race Predictor for comparison.
- **Run detail**: a list of every activity and a page per activity with the route on an OpenStreetMap map, per-second charts, HR zones, laps, EF and decoupling, and a report generated by fixed rules.

Every number links back to a documented formula and configurable parameters. Garmin's own figures appear only as a reference.

## Status

All commands work: `runsync sync` pulls activities and daily summaries from the Personal API and a few metrics from garminconnect, `runsync login` stores a garminconnect token, `runsync import-export` loads Garmin's account data export, and `runsync rebuild` rebuilds the analysis database from the raw archive. The dashboard shows weekly volume, training load, the aerobic trend, long runs and race predictions, plus an activity list (`#/runs`), a detail page per activity (`#/run/<id>`), the 5K plan (`#/plan`) and a review of the pushed plan (`#/review`). Tickets live in `.scratch/running-tool/issues/`; deviations from the spec that still need a decision are listed in `.scratch/running-tool/deviations.md`.

## Architecture

- **Rust CLI (`runsync`)**: syncs from the official Garmin Connect Personal API, stores raw FIT and JSON files unchanged in a data directory outside the repository, and builds a SQLite analysis database from them.
- **Python analysis package**: polars and DuckDB over the read-only analysis database; also usable from Jupyter.
- **Dashboard**: FastAPI bound to `127.0.0.1`, serving JSON to a static frontend (plain HTML, native ES modules, hand-written SVG charts).

## Data directory

Both projects find their data through `RUNNING_DATA_DIR`, defaulting to `%USERPROFILE%\running-data`. It holds `config.toml`, the hand-kept `races.csv`, the raw archive (`raw/`), credentials (`secrets/`), cooldown markers and the record of pushed plan workouts (`state/`) and the analysis database `running.sqlite`.

`config.toml` (only `[[physiology]]` is required; every other key shows its default):

```toml
[[physiology]]                  # one block per change; each activity uses the set in effect on its date
effective_from = 2021-08-01
hr_max = 192
hr_rest = 55
lthr = 170

[aerobic]
reference_hr = 145              # GAP pace is read off at this heart rate
warmup_s = 600                  # moving time dropped at the start of each run
smoothing_s = 30                # trailing mean for HR, speed and altitude
hr_band_bpm = 15                # steady seconds: smoothed HR within reference_hr +- this
speed_window_s = 60
max_speed_change = 0.05         # (max - min) / mean of smoothed speed in that window
min_hr_spm_gap = 5              # |HR - spm| below this looks like cadence lock
min_steady_s = 600              # runs with less steady time are left out
grade_window_s = 30
grade_start_s = 120             # no grade (GAP = pace, no altitude change) while the altimeter settles
max_grade = 0.15
min_runs_per_week = 2
rolling_weeks = 4
max_speed_mps = 7.0             # per-second speed above this is suspect (GPS drift)
max_fast_s = 60                 # runs with more seconds above max_speed_mps are left out
hot_week_c = 22.0               # weeks with median air temperature at or above this are marked hot

[run_walk]
cadence_spm = 140               # smoothed cadence (both feet) at or above this is running
smoothing_s = 10
min_walk_s = 10                 # shorter walking stretches still count as running
pause_gap_s = 10                # a longer gap between samples is a pause

[load]
max_sample_gap_s = 10           # a longer gap between HR samples counts only this long in TRIMP

[zones]
lthr_pct = [85, 90, 95, 100]    # HR zone floors in % of LTHR: Z1 below 85 %, Z5 at or above 100 %

[report]                        # thresholds of the detail page's report rules
interval_speed_ratio = 0.10     # a rep is this much faster than the run's median speed
interval_min_s = 60             # a rep lasts at least this long
interval_min_reps = 3           # an interval session has at least this many reps
tempo_share = 0.5               # Z3-Z4 share of the running time for a tempo run
tempo_min_s = 900               # ... with one unbroken Z3-Z4 stretch at least this long
long_easy_share = 0.7           # Z1-Z2 share of a long run (60 minutes or more)
easy_share = 0.8                # Z1-Z2 share of an easy run
aerobic_change = 0.02           # aerobic value this much above/below the baseline
split_change = 0.02             # second half's GAP pace this much faster/slower

[sync]
personal_api_interval_s = 1.5   # pause between Personal API requests
garminconnect_interval_s = 5.0  # pause between garminconnect requests
```

`races.csv` lists your races by hand, UTF-8 (saving from Excel with a BOM is fine). First line and an example:

```csv
date,activity_id,distance_m,time_s,all_out,note
2026-04-12,21234567890,21097.5,5880,yes,city half marathon
```

`activity_id` may be empty; `all_out` is `yes` or `no` (also `true`/`false`, `1`/`0`, `y`/`n`, `是`/`否`). Only all-out races from the last 6 months drive the predictions. The dashboard says when the file is missing or malformed.

`runsync sync` reads the Personal API key from `secrets/personal_api.key` (the bare key on one line; generate it at https://connect.garmin.com/app/settings/personalApiToken). It downloads every activity's detail JSON and FIT into `raw/personal_api/activities/` and daily summaries into `raw/personal_api/daily_summaries/`, loading each file into `running.sqlite` straight away. Rerun it after an interruption to resume. Later runs fetch only new activities and refetch details from the last 7 days. It then fetches garminconnect metrics (race predictor and others) into `raw/garminconnect/` if `runsync login` has stored a token in `secrets/garminconnect/`; without a token that source is skipped. A source that is rate limited stops at once and is skipped for 24 hours (marker in `state/`, delete it to retry sooner); a rejected key or token ends with how to replace it.

### Importing the Garmin account export

The full history can come from Garmin's account data export instead of thousands of API requests:

1. Request the export in your Garmin account (Account > Data Management > Export Your Data) and download the zip from the e-mail Garmin sends.
2. Run `runsync import-export <path to the zip>`. It copies the zip unchanged to `raw/export/<export date>/` (the newest modification date inside the package), then loads activities, activity FIT files, daily summaries and Garmin's VO2max, race predictor and training status from that copy into `running.sqlite`. It prints counts and date ranges, including FIT files skipped because they are not activities (daily monitoring and the like). Importing the same zip again changes nothing; a newer export overrides an older one. Data already downloaded from the APIs takes precedence over the export. Sleep, profile and the rest of the package are archived but not parsed.
3. Run `runsync sync` as usual. Activities and days the export already holds are not requested again, so only data after the export date (plus the usual 7-day refresh and today's Garmin metrics) is fetched.

`runsync rebuild` loads the archived exports again. The export contains GPS tracks and your e-mail address: keep it in the data directory, never in the repository.

An export FIT file carries no activity id, so it is matched to an activity by start time: an exact match first, otherwise the only activity starting within 120 s of it. Activity summaries (distance and so on) stay Garmin's; the FIT only provides the per-second records and laps. The export has no time zone name, so `activities.time_zone` for an export activity is `Pacific/Auckland` when the local start's offset matches Auckland's at that moment, and otherwise a fixed offset such as `+08:00`; activities from the Personal API keep their IANA name. `daily_wellness.resting_hr_bpm` is always empty: the watch is worn in the daytime only, so Garmin's resting heart rate is too high to use. The analysis takes the resting heart rate from `hr_rest` in `config.toml`. The raw files keep Garmin's value.

### Air temperature from Open-Meteo

`runsync sync` also fetches hourly air temperature from the free [Open-Meteo historical weather API](https://open-meteo.com/en/docs/historical-weather-api) (no key) for the aerobic chart. It runs after the two Garmin sources and independently of them.

What is sent: one grid point, rounded to 0.1° (about 10 km), and a date range. The grid point is the most common one among road runs (`running`, `street_running`) with GPS: each run's median latitude and longitude are rounded to 0.1° and the most frequent result wins. Nothing else (no tracks, times or account data) leaves the machine. Without a road run with GPS, nothing is requested. It asks for every day from the first road run to two days ago that has no temperature yet for that grid point, one request per run of consecutive missing days. The archive may hold only empty (null) hours for the latest days; such days count as missing and are asked for again on a later sync. If the main grid point moves, only the new one is fetched; the old archive stays.

Each response is stored verbatim in `raw/open-meteo/<start>_<end>.json`, next to `<start>_<end>.request.json` recording the grid point and dates asked for, and loaded into the `hourly_weather` table (UTC hours). `runsync rebuild` loads the archive again; an empty hour never replaces a temperature. Without an analysis database Open-Meteo is skipped; otherwise each run is recorded in the `sync_runs` table with source `open_meteo`. A rate limit (HTTP 429) skips Open-Meteo for 24 hours (`state/open_meteo.cooldown.json`). Messages and logs never show the grid point or the request URL; the archive files hold it, so keep them in the data directory.

## Run detail and report

The activity list shows every activity, newest first, running only (default) or all types, with an optional minimum distance. Each row opens the detail page: summary, route map, per-second pace/HR/cadence/altitude charts with the steady seconds marked, time in each HR zone, laps, EF and decoupling, and the report on top.

The report applies fixed rules, one line each, with the rule and the numbers behind it a click away. Thresholds come from `[report]`, `[zones]` and `[aerobic]`:

- **训练类型** (training type): interval, tempo, long, easy or mixed, from fast reps and HR-zone shares.
- **有氧能力对比**: this run's aerobic value against the median of every valid run in the 4 weeks (`rolling_weeks`) before its week.
- **心率漂移**: decoupling of runs of 60 minutes or more; above 5 % is flagged.
- **配速分布** (pacing): GAP pace of the second half of the distance against the first half; not judged for intervals.
- **负荷**: TRIMP, TSB before and the day after, and the load-spike warning (ATL/CTL above 1.5).
- **气温**: listed only when the run has an air temperature; at or above `hot_week_c` it is flagged.

A rule that cannot judge (no HR, no GPS, treadmill, not a run) says why instead of guessing. EF and decoupling use the same steady seconds as the aerobic value but without the HR band, so drift out of the band still shows.

API (JSON, all on `127.0.0.1:8765`): `GET /api/activities?type=running|all&min_km=&page=&page_size=` (page size up to 200) for the list, `GET /api/activities/{activity_id}` for the detail plus report (404 with a Chinese message when the id is unknown). The route is sent as the simplified track (at most 500 points) in latitude and longitude, plus a normalised shape. The browser draws it on tiles from `tile.openstreetmap.org`, so the tile server sees the approximate area of each run you open.

## Pushing the 5K plan to Garmin Connect

`uv run running-push-plan` (in `analysis/`) turns the 8-week 5K plan into Garmin structured running workouts and, with `--apply`, puts them on the Garmin Connect calendar; the watch gets them at its next sync with Garmin Connect. Without `--apply` it is a dry run: it prints each workout (date, steps, pace ranges) and sends nothing.

- Options are the dashboard's: `--target 20:00`, `--days 2,3,4,6` (1 = Monday), `--parkrun 6` (`0`: none), `--current mm:ss`. The settings are checked against the dashboard's bounds (5K times 10:00 to 1:00:00). Week 1 starts on `--start` (a Monday), default today when today is a Monday, else the coming Monday; the preview prints the start and end dates.
- Each run day is one workout named `5K W<week> <day> <title>`, e.g. `5K W1 Tue 5x1km @I`. Everything the watch shows (names, descriptions, step notes) is English, since Garmin watches show Chinese as garbage; the dashboard keeps the Chinese. Easy and long runs are one distance step at the week's E pace range; quality days are a 3 km warm-up, the reps as repeat groups (recovery by time or distance as the plan says, last recovery skipped), a lap-button jog between parts and a 2 km cool-down; parkruns and the race are warm-up, 5 km at the session's target time and cool-down. Single paces get a range of plus or minus 5 s/km.
- The push runs `importer/garminconnect/garmin_metrics.py push` with the `runsync login` token (it writes to your Garmin account, so run it yourself). It uploads and schedules one workout at a time, 2 s apart (`--interval`), then asks Garmin to send scheduled workouts to the devices.
- A rate limit (HTTP 429 or CAPTCHA) writes the same 24-hour marker `runsync sync` uses (`state/garminconnect.cooldown.json`); while it is active, pushes are refused and `runsync sync` skips garminconnect. Delete it to retry sooner.
- The ids it creates are recorded in `state/plan5k_push.json` after every step. A second `--apply` refuses to create duplicates; `--apply --replace` first deletes exactly the workouts listed there (and with them their calendar entries), then pushes the current plan. After an interrupted push, `--apply --replace` cleans up and starts again.
- The record also keeps the push settings and each workout's steps. The dashboard's plan review (`#/review`, `GET /api/plan-review`) reads it: each scheduled session is matched with the longest run of its date and judged against those steps. Quality sessions: the reps are found in the per-second records and each rep's pace is checked against its range. parkruns and the race: the fastest continuous 5 km against the planned time, and the first km. Easy and long runs: distance, and pace only when faster than E. Warm-up and cool-down are listed, but a short one never counts against a session. Cadence (spm, both feet) and stride (distance / steps) are shown for the whole run, each rep and each race km; they are not judged. A record from before the steps were kept is rebuilt from its settings (or the defaults) and its push date, with a warning.

## Common commands

Importer (run in `importer/`):

```sh
cargo build --release          # binary at target/release/runsync.exe
cargo run -- sync              # fetch new data from the Personal API and garminconnect (RUST_LOG=debug for detail)
cargo run -- login             # log in to garminconnect once and store the token (interactive)
cargo run -- import-export <zip>   # archive and load a Garmin account export, offline
cargo run -- rebuild           # delete running.sqlite and rebuild it from raw/, offline
cargo test
cargo fmt
cargo clippy --all-targets -- -D warnings
```

Analysis and dashboard (run in `analysis/`):

```sh
uv sync
uv run python scripts/fetch_fonts.py   # once: download the self-hosted fonts (not committed)
uv run running-dashboard               # http://127.0.0.1:8765
uv run running-push-plan               # preview the 5K plan as Garmin workouts; --apply to push (writes to Garmin)
uv run pytest
uv run ruff format
uv run ruff check
uv run python scripts/db_summary.py   # read-only counts, date ranges, NULLs, aerobic totals (no coordinates)
```

Tests never touch the real data directory; they build temporary ones and point `RUNNING_DATA_DIR` at them.

## Notebooks

`analysis/notebooks/explore.ipynb` is the starting point for exploring your data. It calls the same public functions as the dashboard (weekly volume, training load, aerobic trend, per-run tables, per-second steady-state data), so its numbers match the dashboard.

Start JupyterLab (it is in the `dev` dependency group, which `uv sync` installs):

```sh
cd analysis
uv sync
uv run jupyter lab notebooks/explore.ipynb
```

The notebook reads `RUNNING_DATA_DIR` (default `%USERPROFILE%\running-data`); set it before starting Jupyter to point at another data directory.

In VS Code: run `uv sync` in `analysis/` first, open the notebook, click **Select Kernel** (top right), choose **Python Environments**, and pick `analysis\.venv\Scripts\python.exe` (shown as `.venv`). If it is not listed, use **Python: Select Interpreter** > **Enter interpreter path** with that path. The Jupyter and Python extensions are needed; `ipykernel` comes with `jupyterlab`.

Notebook outputs can contain personal data, so `.gitattributes` strips them on commit with `nbstripout`. Set up the filter once per clone (from the repository root):

```sh
git config filter.nbstripout.clean "uv run --directory analysis nbstripout"
git config filter.nbstripout.smudge cat
git config filter.nbstripout.required true
git config diff.ipynb.textconv "uv run --directory analysis nbstripout -t"
```

## Privacy

No credentials, raw activity files, or databases are committed. API keys and session tokens live in the data directory outside the repository. The physiology parameters in the docs (HRmax, resting HR, LTHR) are the author's own and are kept because the design decisions depend on them.
