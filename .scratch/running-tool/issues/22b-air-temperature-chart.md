## Agent Brief

> *This was generated by AI during triage.*

**Category:** enhancement
**Summary:** the analysis package reads air temperature from the hourly table created in 22a: interpolate an air temperature for each valid road run, change the weekly temperature to the weekly median air temperature, and mark weeks with a median ≥ 22 °C as hot weeks on the aerobic chart; aerobic fitness values are not corrected.

**Current behavior:**
`aerobic_runs` computes `temperature_c` for each run as the mean of the per-second `records.temperature`; the weekly series' `temperature_c` is the mean of those values; the dashboard's aerobic chart draws temperature bars below, and points out "the hottest week" in the hint (when it is more than 5 °C above the median). In the real data `records.temperature` is all NULL, so the temperature bars and the hint are always empty.

**Desired behavior:**
- **Run air temperature**: midpoint = `start_time_utc` + half the total duration. Linearly interpolate between the whole hours before and after it in the air temperature table; NULL when one of the hours is missing or the two hours are more than 1 hour apart. Only runs near the grid point get an air temperature: after rounding the activity's median latitude and longitude to 0.1°, both must differ from the air temperature table's grid point by ≤ 0.2° (compare with 0.21 to avoid floating-point error); otherwise NULL. When the air temperature table has several grid points, take the nearest.
- **Weekly air temperature**: the weekly series' `temperature_c` becomes the median air temperature of that week's valid road runs ("valid" as judged for aerobic fitness).
- **Hot weeks**: weeks with a median weekly air temperature ≥ `hot_week_c` (`[aerobic]` in `config.toml`, default 22.0) are marked `hot = true`. The dashboard's aerobic chart marks these weeks (e.g. a light background band, with the legend "高温周（≥ 22 °C）" (hot week, ≥ 22 °C)); the old "hottest week" hint is now based on hot weeks. Aerobic fitness values themselves are not corrected.
- **Missing table**: when the analysis database has no air temperature table (databases from before 22a) or the table is empty, air temperature is NULL without an error; the dashboard shows no temperature bars and no hot weeks.
- **Method description**: the `method` of the aerobic fitness JSON states: air temperature comes from Open-Meteo historical weather (one 0.1° grid point, interpolated at the run's midpoint), no temperature correction is made (19's outcome: R² 0.002), and the definition and threshold of a hot week.
- `records.temperature` is no longer read (drop this column when loading per-second records).

**Key interfaces:**
- The `temperature_c` column of `aerobic_runs(db, config, ...)`: its source switches to the air temperature table.
- The weekly series (`aerobic_trend` and `temperature_c` in the weekly structure): becomes a median, with a new `hot: bool`.
- The `Aerobic` dataclass gains `hot_week_c: float = 22.0`, read by `load_config`, with the README config example updated.
- Aerobic fitness JSON: each week gains `hot`; `method` keeps the `{name, description, params}` structure, and `params` gains `hot_week_c`.
- The dashboard's aerobic chart (frontend): draws hot-week markers, and the temperature bars use the new weekly air temperature.

**Acceptance criteria:**
- [x] Tests (synthetic analysis database): a midpoint between two whole hours is interpolated proportionally; a midpoint on a whole hour takes that value; a missing hour gives NULL
- [x] Test: runs within 0.2° of the grid point have air temperature, runs 0.3° away do not
- [x] Test: the weekly air temperature is a median; of two weeks with medians of 21.9 and 22.0 °C, only the latter is `hot`; changing `hot_week_c` changes the result accordingly
- [x] Test: an old database without the air temperature table still computes aerobic fitness, with NULL air temperature
- [x] JSON API tests cover `hot` and the new text in `method`
- [x] The temperature bars and hot-week markers are visible on the dashboard in a browser (checked with synthetic data or a screenshot of the real database opened read-only; screenshots do not go into git)
- [x] `ruff format --check`, `ruff check` and `pytest` pass
- [x] After 22a's HITL is done, check the real database read-only: the number of valid road runs with air temperature (608 in 19) and the number of hot weeks (14 in 19), outputting only aggregate numbers

**Out of scope:**
- Fetching air temperature and creating the table (22a)
- Regression correction of pace by air temperature; the reference temperature 17 °C is only recorded, not used for now
- Changing `config.toml` and `running.sqlite` in the data directory
