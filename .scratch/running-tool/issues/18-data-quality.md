### 2. GPS drift

- **Distance consistency**: ratio of cumulative per-second distance to activity distance is 1.0 at the 1st, 50th and 99th percentiles; 0 activities deviate by more than 5%.
- **Speed distribution** (`running`)
  - Mean speed: 1st, 50th, 99th percentiles 2.59, 3.15, 4.10 m/s, no outliers.
  - `max_speed`: median 4.02, 99th percentile 8.47, 13 above 7 m/s.
- **Per-second speed > 7 m/s** (faster than 2:23 /km, which the user cannot run)
  - Symptom: 315 seconds in total, in 13 activities; 261 of them > 8 m/s.
  - The worst is `15966492890` (2024-06-18, 12.1 km): 171 seconds > 7 m/s, up to 20.6 m/s, about 3.5 km accumulated in those seconds. At normal pace that time covers only about 0.5 km, so this run's distance is about 3 km too long.
  - Each of the other 12 activities has only 1–33 seconds.
- **Impact**
  - Load: none, TRIMP uses only heart rate.
  - Volume: about 3 km extra in the week of `15966492890`, the rest negligible.
  - Aerobic fitness: 4 of the 13 are judged valid.
    - `15966492890` has a pace of 294.6 s/km, while the median pace of valid road runs is 322.6, so this run is clearly too fast.
    - `13567707685`, `17154272874` and `19353635816` each have only 1–5 seconds over the limit, negligible.
- **Recommendation**: flag only, do not change distance.
  - Aerobic fitness: if an activity has more than 60 s accumulated at > 7 m/s, judge it invalid. Under this rule only `15966492890` is currently excluded.
  - Volume: keep Garmin's distance.
  - The two thresholds (7 m/s, 60 s) go into `config.toml`.

### 3. Pauses: time difference between adjacent samples

| Gap | Count |
| --- | --- |
| ≤ 1 s | 3351819 |
| 1–2 s | 2027 |
| 2–5 s | 2820 |
| 5–10 s | 5449 |
| 10–30 s | 174 |

- Nearly all 2–10 s gaps are in 2021: 8185 of them, in 32 activities, caused by smart recording. After that only 9–21 per year.
- For all gaps > 10 s, the median speed before the gap is about 3 m/s and after it always 0. So 10–30 s gaps, like longer ones, are resumptions after a pause.
- Impact: `pause_gap_s = 30` counts 10–30 s pauses as running. There are only 174 such stretches in the whole history, each at most 20 s, negligible. `max_sample_gap_s = 10` already covers the 2–10 s gaps of 2021.
- Recommendation:
  - Change `pause_gap_s` from 30 to 10, matching `max_sample_gap_s`.
  - Keep `max_sample_gap_s` at 10.

### 5. Problems already found

- **`resting_hr_bpm` is unusable**
  - Symptom: 1050 of 1913 days have a value, with 10th, 50th, 90th percentiles of 66, 106, 130. On 1015 of those days it is above that day's `min_hr_bpm`.
  - Impact: the analysis package does not read this column, so currently none.
  - Recommendation: stop importing it, writing NULL on import. The raw archive stays as is, so it can be rebuilt if needed later. Explain why in `conventions.md`, to prevent future misuse.
- **`min_hr_bpm` is a daytime value**
  - Symptom: 1387 days have a value, with 10th, 50th, 90th percentiles of 54, 65, 81.
  - Recommendation: keep it. `hr_rest = 55` is already set by hand from the 10th percentile; no code change needed.
- **2 activities without per-second records**
  - `9136530487` (2022-07-04, running, 12500 m, 3733.5 s):
    - The unmatched FIT in the export package is this one's. The FIT's session start time is 50 s later than `beginTimestamp`. The FIT has 3734 records, 14 laps, distance 13003 m.
    - The activity distance is the round number 12500; it looks like the user edited it by hand in Garmin Connect, so exact matching by start time fails.
    - Recommendation: when exact matching fails, match the FIT to the single nearest activity within ±120 s. After the change, run `runsync rebuild`, and this run gets per-second records. The activity summary keeps Garmin's values.
  - `8234857240` (2022-02-04, running, 6240.7 m, 1869.9 s):
    - Its FIT is neither in the export package nor in `raw/personal_api/activities`.
    - Impact: load falls back to the activity summary's average heart rate; aerobic fitness has 1 run fewer.
    - Recommendation: ignore. Alternatively, download this FIT separately through the API later.
- **Export package activities have no `time_zone`**
  - Symptom: 1095 activities have NULL `time_zone`; only the 4 from the API have `Pacific/Auckland`. Computing the offset as `start_time_local − start_time_utc`: 556 at +13 h, 533 at +12 h, 6 at +8 h.
  - +12 h and +13 h are New Zealand standard time and daylight saving time.
  - Impact: the analysis package does not read `time_zone`; local dates use `start_time_local` directly, so currently none.
  - Recommendation: when importing the export package, infer the time zone from the offset.
    - When the offset matches `Pacific/Auckland`'s offset at that moment, write `Pacific/Auckland`.
    - Otherwise (currently the 6 at +8 h) write a fixed offset, e.g. `+08:00`, without guessing a city.
    - Note in `conventions.md` that `time_zone` may be a fixed offset.
