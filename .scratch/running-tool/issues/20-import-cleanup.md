## Agent Brief

> *This was generated by AI during triage.*

**Category:** enhancement
**Summary:** 导入端三处清洗：导出包 FIT 匹配活动允许 ±120 s 容差；导出包活动推出 `time_zone`；`resting_hr_bpm` 不再导入。

**Current behavior:**
- 导出包的 activity FIT 只在 session 开始时间（Unix 秒）与活动 `beginTimestamp / 1000` 完全相等时才对应到活动；真实包有 1 个 FIT 因为晚 50 s 对不上，计为"matching no activity"。
- 导出包活动的 `time_zone` 一律为 NULL（导出包只有 Garmin 内部的时区 id）；Personal API 来的活动有 IANA 时区名。
- 每日汇总的 `resting_hr_bpm` 从导出包 UDS（`restingHeartRate`）和 Personal API（`heartRate.restingValue`）写入。用户只在白天戴表，这个值偏高，不可用。

**Desired behavior:**
- FIT 匹配：先精确匹配；没有精确匹配时，取开始时间相差 ≤ 120 s 的活动，候选必须唯一（同样最近的有两个以上、或窗口内有两个以上候选时都不匹配，仍计为"matching no activity"）。已经被别的 FIT 精确匹配的活动不能再被容差匹配覆盖。活动汇总值不变，FIT 只提供 `records` 和 `laps`。
- `time_zone`：导出包活动用 `start_time_local − start_time_utc` 得到偏移。偏移等于 `Pacific/Auckland` 在该 UTC 时刻的偏移（含夏令时）时写 `Pacific/Auckland`，否则写固定偏移字符串，格式 `+08:00` / `-05:30`。API 活动不变；API 优先规则不变。
- `resting_hr_bpm`：导出包和 Personal API 两条路径都写 NULL；原始档案不改。
- `rebuild` 与直接导入结果一致（三条都适用）。
- 文档：`activities.time_zone` 和 `daily_wellness.resting_hr_bpm` 的 migration 列注释更新（不改已有 migration 的 SQL 语义；只改注释，或新增 migration，由实施决定，但已有库上的迁移测试必须通过），README 加一句说明。

**Key interfaces:**
- 导出包加载器里按开始时间查活动的映射（现在是开始秒 → activity_id 的精确查找）：改为支持"精确优先、否则唯一最近且 ≤ 120 s"。容差 120 s 写成命名常量。
