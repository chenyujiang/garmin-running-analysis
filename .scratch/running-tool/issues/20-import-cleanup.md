## Agent Brief

> *This was generated by AI during triage.*

**Category:** enhancement
**Summary:** three cleanups on the import side: export package FIT-to-activity matching allows a ±120 s tolerance; export package activities get an inferred `time_zone`; `resting_hr_bpm` is no longer imported.

**Current behavior:**
- An export package activity FIT is mapped to an activity only when the session start time (Unix seconds) exactly equals the activity's `beginTimestamp / 1000`; in the real package 1 FIT is 50 s late, does not match, and counts as "matching no activity".
- Export package activities always have NULL `time_zone` (the export package only has Garmin's internal time zone id); activities from the Personal API have an IANA time zone name.
- The daily summary's `resting_hr_bpm` is written from the export package UDS (`restingHeartRate`) and the Personal API (`heartRate.restingValue`). The user only wears the watch during the day, so this value is too high and unusable.

**Desired behavior:**
- FIT matching: exact match first; without an exact match, take the activity whose start time differs by ≤ 120 s, and the candidate must be unique (if two or more are equally near, or there are two or more candidates in the window, it does not match and still counts as "matching no activity"). An activity already matched exactly by another FIT cannot be overridden by a tolerance match. Activity summary values are unchanged; the FIT only provides `records` and `laps`.
- `time_zone`: export package activities get the offset from `start_time_local − start_time_utc`. When the offset equals `Pacific/Auckland`'s offset at that UTC moment (including daylight saving), write `Pacific/Auckland`; otherwise write a fixed offset string in the format `+08:00` / `-05:30`. API activities are unchanged; the API precedence rule is unchanged.
- `resting_hr_bpm`: both the export package and the Personal API paths write NULL; the raw archive is not changed.
- `rebuild` gives the same result as importing directly (for all three).
- Docs: update the migration column comments for `activities.time_zone` and `daily_wellness.resting_hr_bpm` (without changing the SQL semantics of existing migrations; either change only the comments or add a new migration, as implementation decides, but the migration tests on existing databases must pass), and add a sentence to the README.

**Key interfaces:**
- The mapping in the export package loader that looks up activities by start time (currently an exact lookup from start second to activity_id): change it to support "exact first, otherwise the unique nearest within ≤ 120 s". The 120 s tolerance is a named constant.
- Where the export package activity DTO is converted to `Activity`: `time_zone` is inferred from the offset. Computing the time zone needs the rules of `Pacific/Auckland`; the `chrono-tz` dependency may be added.
- The `resting_hr_bpm` value in both daily summary write paths (export package UDS and Personal API daily summary).
