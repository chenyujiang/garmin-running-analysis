## Agent Brief

> *This was generated by AI during triage.*

**Category:** enhancement
**Summary:** 给 `runsync` 加 Open-Meteo 数据源：算出常跑地点的 0.1° 格点，只请求缺少日期的逐小时气温，原样存档，并载入分析库的新表。

**Current behavior:**
`runsync sync` 依次跑 Personal API 和 garminconnect 两个数据源（各自独立，限流时写冷却标记，见 `sync_all` 和 `cooldown`），每个数据源在 `sync_runs` 记一行。分析库里没有任何气温：`records.temperature` 全是 NULL（FR245 Music 的 FIT 不记录温度）。19 在数据目录的 `raw/open-meteo/` 手动留下过一个缓存文件（`hourly_temperature_2m_<start>_<end>.json`），里面没有记录请求的格点。

**Desired behavior:**
- **格点**：取路跑类活动（`running`、`street_running`，与分析包的 `AEROBIC_TYPES` 一致）中有 GPS 的活动，每个活动的经纬度中位数各四舍五入到 0.1°，出现次数最多的格点就是主格点。没有任何 GPS 时不请求，`sync` 输出一行说明后跳过。
- **请求**：`https://archive-api.open-meteo.com/v1/archive`，参数只有 `latitude`、`longitude`（主格点，一位小数）、`start_date`、`end_date`、`hourly=temperature_2m`、`timezone=GMT`。不需要 key。日期范围是最早一次路跑的日期到"今天 − 2 天"中尚未存档的日期；已存档的日期不再请求。一次请求可以覆盖整段缺失范围（5 年约 4.6 万小时，响应约 1 MB）。
- **存档**：响应原样写入 `raw/open-meteo/`（原子写入），同时记下请求用的格点和日期范围（文件名或旁边的元数据文件，由实施决定），因为响应里的经纬度是模型格点，不等于请求的格点。19 留下的旧缓存没有记录格点，不需要兼容（忽略它，第一次 `sync` 重新请求全部日期）。主格点变了时，只为新格点请求缺失的日期；旧格点的存档保留。
- **分析库**：新 migration 建表（例如 `hourly_weather`），每行是一个格点的一个整点：`grid_lat`、`grid_lon`（请求的 0.1° 格点）、`time_utc`（遵守现有时间列格式）、`temperature_c`；主键是格点加时间。`sync` 存档后载入；`rebuild` 遍历 `raw/open-meteo/` 全部重新载入，结果与 `sync` 一致。
- **失败处理**：Open-Meteo 是独立数据源。网络错误或非 2xx 时这个数据源记为失败，另外两个照常；收到 429 时复用现有冷却机制（单独的冷却标记）。`sync_runs` 记一行，`source = 'open_meteo'`（更新 `sync_runs` 的列注释）。
- **隐私**：格点和坐标只出现在数据目录（原始档案和分析库）里。`sync` 输出、错误信息、日志都不能带坐标；HTTP 库的错误常常带完整 URL，要去掉（例如 `reqwest::Error::without_url`）。输出只写小时数和日期范围。
- **证书**：本机 Python 的证书链验证这个站点失败（见 19），系统 `curl`（schannel）正常。Rust 端用现有的 HTTP 客户端，正常验证证书；如果验证失败，换 TLS 后端或根证书来源，不能关闭验证。

**Key interfaces:**
- 新的气温数据源 trait（仿照 `ActivitySource`、`MetricsSource`），让测试能注入假数据源；真实实现用现有的 `reqwest` 客户端。
- `sync_all` 的报告 `SyncAllReport` 增加 Open-Meteo 的 `Outcome`；`sync` 命令输出它的一行。
- `rebuild` 的 `RebuildReport` 增加载入的气温小时数。
- 新 migration（编号接在现有最后一个之后）。
