# Single-run detail and analysis report: implementation spec

Label: ready-for-agent
Status: open

Source: the user's request on 2026-11-04 and their confirmation of the plan (link from the activity list to a detail page; the map draws only the SVG route shape, with no base map; the analysis report is generated by fixed rules). The previous phase's spec is in [running-tool/spec.md](../running-tool/spec.md), with deviations in [running-tool/deviations.md](../running-tool/deviations.md). Terms are in `GLOSSARY.md` at the root, product background in `PRODUCT.md`.

## Problem Statement

The dashboard currently has only summaries: weekly volume, training load, the aerobic fitness trend, the long-run table, race prediction. After a run, the user wants to look at that run itself: how pace and heart rate changed, how each kilometre and each lap went, whether it counts as an easy run or a tempo run, whether aerobic fitness was better or worse than recently, whether heart rate drifted, whether heat had an effect. Today that means querying it in Jupyter by hand, or going back to Garmin Connect's black-box numbers.

## Solution

The dashboard gains two pages, both in the same static frontend, with hash routing:

- **Activity list** `#/runs`: activities in reverse order of start time, filterable by type and distance, paged. Each row links to the detail page. Activities in the home page's long-run table and recent races table also link to the detail page.
- **Activity detail** `#/run/<activity_id>`: summary, per-second curves, splits (laps and per kilometre), route shape, metrics for this run, and at the top a Chinese analysis report generated by fixed rules.

Everything is computed on the fly from data already in the analysis database and formulas already in the `running` package: no changes to the Rust side, no schema change, nothing stored. Every sentence of the report can be traced back to a rule and its parameters. Data stays on the machine: the route is drawn only as a shape, and no online base map is loaded.

## User Stories

**Getting to the detail page**

1. As a runner, I want a list of my activities, newest first, so that I can find the run I just did.
2. As a runner, I want to filter the list by activity type (running types by default, or all types), so that strength and cycling sessions don't crowd it.
3. As a runner, I want to filter the list by minimum distance, so that I can find long runs quickly.
4. As a runner, I want each list row to show date, type, name, distance, duration, running pace and average HR, so that I can recognise the run before opening it.
5. As a runner, I want the list paged, so that the page stays fast with 1500 activities.
6. As a runner, I want the runs in the long-run table and recent-race table on the home page to link to their detail page, so that I can drill down from the summary.
7. As a runner, I want the detail page to have its own URL, so that I can bookmark it or reopen it after a refresh.
8. As a runner, I want a clear message when the activity id doesn't exist, so that a stale bookmark doesn't show a blank page.

**Summary and curves**

9. As a runner, I want the summary to show distance, duration, running pace (walking left out), Garmin's average pace as reference, average and max HR, cadence (spm), elevation gain and air temperature, so that I see the run at a glance.
10. As a runner, I want HR, pace, GAP pace, altitude and cadence charts on one shared time axis, so that I can see how they move together.
11. As a runner, I want pauses, walking stretches and steady-state seconds marked on the charts, so that I can see which seconds the metrics used.
12. As a runner, I want a crosshair readout on the charts, so that I can read exact values at any moment.

**Splits**

13. As a runner, I want a table of the watch laps with pace, HR and cadence, so that I can review interval sessions as I ran them.
14. As a runner, I want a table of per-kilometre splits with running pace, GAP pace, HR and cadence, so that I can compare kilometres on a hilly course.

**Route shape**

15. As a runner, I want the route drawn as a shape with start and finish marked, so that I recognise the course.
16. As a runner, I want no map tiles loaded, so that the location of my runs is never sent to a third party.

**Metrics for this run**

17. As a runner, I want this run's TRIMP, so that I know how much it adds to training load.
18. As a runner, I want time in each HR zone, so that I can see how hard the run really was.
19. As a runner, I want this run's aerobic value (pace at reference HR) when the run qualifies, and the reason when it doesn't, so that I trust the trend chart.
20. As a runner, I want EF and, for runs of 60 minutes or more, decoupling, so that I can judge endurance on this run.

**Analysis report**

21. As a runner, I want a short report at the top of the detail page, so that I get the conclusions without reading every chart.
22. As a runner, I want the report to classify the run (easy, tempo, interval, long, mixed), so that I can check the week's mix.
23. As a runner, I want the report to compare this run's aerobic value with my recent 4-week median, so that I know whether it was a good day.
24. As a runner, I want the report to say whether HR drifted (decoupling), so that I know whether the pace was sustainable.
25. As a runner, I want the report to describe the pacing (even, positive or negative split, on GAP pace), so that hills don't fool the verdict.
26. As a runner, I want the report to say what the run did to load (TRIMP, share of the week, TSB before and after), so that I can plan the next days.
27. As a runner, I want the report to warn when the air was hot, so that a high HR has an explanation.
28. As a runner, I want every report sentence to show the rule and thresholds behind it, so that I can disagree with a rule and change its parameter.
29. As a runner, I want the report thresholds in `config.toml`, so that I can tune them without editing code.
30. As a runner, I want the report to say what it couldn't judge and why (no HR, no GPS, too short), instead of guessing.

## Implementation Decisions

**What does not change**

- No changes to the Rust side, no migrations, no change to the analysis database schema. Only existing tables are used: `activities`, `records`, `laps`, `hourly_weather`.
- Derived values are computed each time and not stored. The analysis database is still opened read-only.
- The dashboard still binds only to `127.0.0.1`, is read-only, and writes nothing.

**Analysis package `running`**

- New module `running/activities.py`: the activity list. `activity_list(type_filter="running", min_distance_m=None, page=1, page_size=50, root=None)`. `type_filter` is `running` (the 9 types in `RUNNING_TYPES`) or `all`. Each row: `activity_id, activity_type, activity_name, start_time_local, distance_m, duration_s, running_pace_s_per_km` (running types only), `avg_hr_bpm`. Returns the total count for frontend paging.
- New module `running/detail.py`: a single activity's detail, `activity_detail(activity_id, root=None)`, returning everything the detail page needs at once. Split into internal functions: summary, per-second series, splits, route, metrics for this run. It reuses existing functions and does not copy formulas:
  - Run/walk classification and running pace: `runwalk.classify_records`, `running_summaries`.
  - Steady-state segments, GAP: `aerobic.steady_state`, `gap_speed`; this run's aerobic fitness value uses the same conditions as `aerobic_runs`.
  - Air temperature: `aerobic.air_temperature`.
  - TRIMP: the per-second algorithm in `load`; TSB before and after taken from the `training_load` series (TSB uses the previous day's CTL/ATL, see deviation 2).
  - EF and decoupling: the same definitions as `longruns` (steady-state segments without the heart-rate band condition, steady time split in half). The threshold is an outdoor road run, per-second heart rate, usable GPS, and ≥ 10 minutes of steady state without the heart-rate limit; so a run whose heart rate stays entirely outside 145 ± 15 has no aerobic fitness value but still has EF.
- **Per-second series**: downsampled on the server to at most 1500 points (time split into equal buckets, mean within each bucket, pauses never span a bucket). Pauses, walking and steady state are returned as interval lists (`[start_s, end_s]`, seconds since the start of the activity), not as per-point flags.
- **Per-kilometre splits**: cut by `records.distance`, one split per full 1000 m; the last split under 1 km is listed separately with its distance. Each split gives running pace (running seconds only), GAP pace, average heart rate, average spm, elevation gain and loss.
- **Lap splits**: taken directly from the `laps` table; `avg_cadence` ×2 gives spm.
- **Route shape**: only seconds with `lat`/`lon`. Equirectangular projection onto a metric plane with the route centre as origin, then scaled as a whole into `[0, 1]`, keeping the aspect ratio; simplified with Douglas–Peucker to at most 500 points. Only the normalised `x, y`, the indices of start and finish in the sequence, and the scale (metres per unit of `[0, 1]`) are returned. **The endpoint returns no absolute latitude, longitude or centre point.** Activities without GPS (treadmill and so on) return `route: null` with a reason.
- **Heart-rate zones**: 5 zones as percentages of LTHR (Friel's running zones): Z1 < 85%, Z2 85–89%, Z3 90–94%, Z4 95–99%, Z5 ≥ 100%. LTHR is taken from the `[[physiology]]` entry in effect on the activity date. The bounds go in a new `[zones]` config as a list, `lthr_pct = [85, 90, 95, 100]`. Only seconds with heart rate count; pauses do not.
- **Analysis report**: new module `running/report.py`, `run_report(detail, context) -> Report`; the input is the detail data and recent context (median aerobic fitness value of valid runs in the previous 4 weeks, the week's TRIMP, the TSB series), the output a list of items. Each item: `rule` (rule name), `verdict` (short verdict used for colour: `good`, `neutral`, `watch`, `unknown`), `text` (one Chinese sentence), `params` (thresholds used and actual values). The report is a pure function, easy to test. Rules:
  1. **Training type** (checked in order, first hit wins):
     - Intervals: ≥ 3 stretches where the 30-second smoothed speed is ≥ 15% above this run's median speed for ≥ 60 seconds, with slower recovery stretches between them.
     - Tempo: Z3–Z4 together ≥ 50% of running time, including one continuous stretch of ≥ 15 minutes.
     - Long run: duration ≥ 60 minutes, and Z1–Z2 together ≥ 70%.
     - Easy run: Z1–Z2 together ≥ 80%.
     - Everything else is mixed.
  2. **Aerobic fitness comparison**: this run's aerobic fitness value compared with the median of all runs counting towards aerobic fitness in the 4 weeks (`[aerobic] rolling_weeks`) before this run's week, with no per-week minimum and no weekly medians first. ≥ 2% faster is good, ≥ 2% slower is watch, in between is flat. When this run does not count towards aerobic fitness, give the reason (not an outdoor road run, under 10 minutes of steady state, no heart rate and so on), verdict unknown.
  3. **Heart-rate drift**: for durations ≥ 60 minutes report decoupling, > 5% is watch, ≤ 5% is good. Under 60 minutes give EF only and do not judge drift.
  4. **Pacing**: split the running seconds in half by distance and compare the GAP pace of the two halves. Second half ≥ 2% faster is a negative split, ≥ 2% slower a positive split, in between even. Interval runs are not judged on pacing.
  5. **Load**: this run's TRIMP, its share of the week's (Monday to Sunday) TRIMP, and TSB before the run that day and on the next day. When ATL/CTL > 1.5 that day, reuse the "负荷突增" (load spike) hint, verdict watch.
  6. **Air temperature**: when this run's mean air temperature (Open-Meteo) is ≥ `hot_week_c` (22 °C), note that heart rate may be raised by heat, verdict watch. Without temperature data this item does not appear.
- Report thresholds go in a new `[report]` config, with defaults in code: `interval_speed_ratio = 0.10` (originally 0.15, see ticket 08), `interval_min_s = 60`, `interval_min_reps = 3`, `tempo_share = 0.5`, `tempo_min_s = 900`, `long_easy_share = 0.7`, `easy_share = 0.8`, `aerobic_change = 0.02`, `split_change = 0.02`. There is no separate `hot_c`; `[aerobic].hot_week_c` is reused.
- Non-running activities: the detail page still opens, with summary, heart-rate curve, heart-rate zones and TRIMP; the running-specific parts (running pace, per-kilometre splits, aerobic fitness, pacing, training type) return null with the reason "仅跑步类活动" (running activities only).

**Dashboard**

- New endpoints:
  - `GET /api/activities?type=running|all&min_km=<float>&page=<int>&page_size=<int>` (page_size 1–200, default 50).
  - `GET /api/activities/{activity_id}`: detail plus report, returned at once. 404 when it does not exist, with a Chinese explanation in the JSON.
- Each section's response still carries `method{name, description, params}`, shown directly by the frontend's "怎么算的" (how it is computed).
- Frontend: hash routing lives in `app.js`. `#/` (or empty) is the existing home page, `#/runs` the list, `#/run/<id>` the detail. The page header gains a "全部活动" (all activities) link. New modules `static/runs.js` (list) and `static/run.js` (detail); charts reuse `svg.js` and the crosshair readout approach of the aerobic fitness chart. No chart library, no map library, no node build.
- Visuals follow variant A: newsprint background, ink-black text, red `#b0281f` only for watch-level report items and warnings; numbers in tabular-nums. The report sits at the top of the detail page, one line per item, verdict first, with rule and values expandable.
- In the home page's long-run table and recent races table, rows with an `activity_id` get a link.

**Docs**

- In `PRODUCT.md`, "Deeper digging happens in Jupyter" becomes: reviewing a single run happens on the dashboard's detail page; deeper exploration across activities stays in Jupyter.
- `GLOSSARY.md` gains entries: heart-rate zone, training type, analysis report, pacing.
- `README.md` gains short notes on the new config sections `[zones]` and `[report]` and the new endpoints.

## Testing Decisions

Same principle as the previous phase: verify only through external behaviour. All new features go through Seam 3 (pytest + FastAPI `TestClient`, synthetic `running.sqlite`); no new seam.

- **List endpoint**: ordering, type filter, minimum distance, total count for paging, `page_size` out of range returns 422.
- **Detail endpoint**:
  - 404 and the Chinese explanation.
  - Summary values; point count ≤ 1500 after downsampling, pause intervals not spanning buckets.
  - Number of per-kilometre splits and the distance of the last one; spm conversion of lap splits.
  - Heart-rate zones: time in each zone from synthetic heart rate, and LTHR picked by date after changing parameters.
  - Nulls and reasons for non-running activities.
- **Route privacy**: synthetic data uses a fixed made-up coordinate (not the user's real location, written in the test file). Assert that the returned JSON contains no number close to this coordinate (walk every number in the JSON and compare with the original latitude/longitude), that `x, y` are all in `[0, 1]`, the aspect ratio is kept, and point count ≤ 500. Without GPS `route` is null.
- **Report rules**: each rule gets a synthetic activity for both hit and miss, asserting `rule`, `verdict` and the values in `params`. For example: an activity with 3 fast stretches is intervals, one with 2 is not; a second half 3% faster in GAP is a negative split, 1% is even; 61 minutes with 6% decoupling is watch. Changing `[report]` thresholds changes the verdict.
- The synthetic data generators extend the existing `tests/synthetic*.py`, with no new parallel set.
- No automated frontend tests, as in the previous phase; in the last ticket the user checks by eye on real data.
- Tests never run on the real data directory; tests always set `RUNNING_DATA_DIR` to a temporary directory.

## Out of Scope

- Online map tiles, place names, reverse geocoding.
- Generating the report with an LLM.
- Editing activities (rename, change type), deleting activities, marking races in the dashboard.
- Side-by-side comparison of two activities; comparison of past runs on the same route.
- Power analysis (`records.power` is mostly empty).
- Caching or storing the detail or report.
- Exporting the report (PDF, image).

## Further Notes

- **Privacy**: the route endpoint returns only the normalised shape. Per `CLAUDE.md`, during implementation and checks no real coordinates, grid points or place names are written in chat, logs, commits or tickets; checks on real data report only aggregate numbers and "route shows correctly/incorrectly".
- **Source of heart-rate zones**: Friel's running LTHR zones follow Joe Friel's published material; before writing code, check the bounds (Z1 < 85% and so on) against the original source, and if they differ, follow the source and record it in the ticket.
- **The training type rules are our own**, not from the literature. The thresholds are in config, and after checking with real data in the last ticket they may need one adjustment.
- The user confirmed the plan on 2026-11-04.

## Deviations during implementation (accepted)

- Report items carry a Chinese `name` besides `rule`, `verdict`, `text` and `params`; `rule` uses English ids: `training_type`, `aerobic`, `drift`, `pacing`, `load`, `heat`.
- The air temperature item also appears below the threshold, with verdict neutral; it is absent only without temperature data.
- The report is computed after the sections (`SECTIONS`) and returned as `report: {items, method}`.
- `route_unavailable` is a top-level key of the detail, not inside `route`.
- Non-running activities also get the altitude curve and the route shape.
- The list's filters and page number live in the hash's query string, e.g. `#/runs?type=all&page=2`.
- Downsampling: when there are more than 1500 pause-free stretches, the whole time axis is bucketed together; buckets may then span pauses, and the point count is still ≤ 1500.
